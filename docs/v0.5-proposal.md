# zerowire v0.5 — Scope Proposal

> Status: **DRAFT proposal**. No code in this PR. Intent: pick the smallest
> scope that maximally moves zerowire toward "people install it and it just
> works."

## Where we are at end of v0.4

- v0.1 (merged): HID fast-lane end-to-end demo.
- v0.2 (PR #3, mergeable): USB/IP passthrough framing + TLS 1.3 PSK auth.
- v0.3 (PR #4): Android userspace URB pump.
- v0.4 (PR #5): Android device acquisition + Compose UI + desktop GUI w/ QR pairing.
- CI (PR #6, green, unmerged).
- Hardware E2E on a real Pixel + real USB stick is **still pending** and gates
  the truth of v0.3 and v0.4.
- Known platform gap: **isochronous transfers** are not supported on the
  Android sender path, so USB audio and UVC webcams do not work. Everything
  else (HID, mass storage, MIDI bulk, printers, microcontrollers) should.

We have a lot of code that is "claimed to work." We have very little code that
is "demonstrated to work on real hardware in CI." That is the hole.

---

## 1. Candidate themes

### A. Hardware validation hardening
Stand up a real hardware E2E harness: a Pixel + a USB hub with a small zoo of
devices (HID mouse, HID keyboard, USB mass storage, USB-serial CDC-ACM,
optionally a MIDI controller) wired into a self-hosted GitHub Actions runner.
Every PR runs the full pair → enumerate → read/write loop against real
silicon. Once this exists, v0.2/v0.3/v0.4 stop being "we think this works"
and become "CI fails if it stops working." Pure plumbing — but it is the
plumbing that converts the existing code into a product we can ship.

### B. Isochronous transfers via UsbRequest queue
Audit Android's `UsbDeviceConnection` + `UsbRequest` async API surface and
determine, with code prototypes (not hand-waving), whether isochronous URBs
can be pumped through a queued `UsbRequest` ring. If yes, we unlock USB audio
DACs and UVC webcams, which are the two highest-demand device classes we
currently do not support. If no, we get a documented dead-end and stop people
asking. High product upside, but research-gated and there is a real chance
the answer is "Android's public API genuinely cannot do it."

### C. Windows receiver
Ship a working Windows receiver using `usbip-win2` (or a thin userspace
shim). Windows is by far the largest desktop audience for a "phone as USB
hub" product. Today we have a Linux receiver and nothing else, which caps
addressable users brutally. Cost: driver signing, installer UX, a Windows CI
lane.

### D. macOS receiver
DriverKit `IOUserUSBHostDevice` system extension. Smaller audience than
Windows, far more painful per device class to ship, requires Apple developer
account and notarization. Probably v0.7+.

### E. Reverse direction (desktop sender → Android receiver)
Share a host USB device to an Android tablet — e.g. plug a SteelSeries
controller into a Linux desktop, have it appear on the tablet. Interesting,
but doubles the test matrix and there is no clear "I needed this yesterday"
demand. Defer.

### F. Multi-device support in one session
Today: one zerowire session carries one device. Multi-device means a phone
with a USB hub plugged in can publish all attached devices in one session.
Mostly a session-multiplexer change; the framing already supports it. Nice
to have, not the bottleneck.

### G. Pairing security: rotate PSK, revoke, expiry
v0.2's PSK pairing is "set once, lives forever." For anything resembling a
real product we need: PSK rotation, per-receiver PSKs, revoke a lost laptop,
optional expiry. Modest scope, important before any "use it daily" claim.

### H. Observability
Structured logs (`tracing` on Rust side, `Timber`/`slf4j`-style on Android),
basic counters (bytes transferred, URBs/sec, reconnects), and an opt-in
crash reporter (Sentry-style, self-hostable). Critical the first time a real
user files a bug we cannot reproduce. Cheap to add now; expensive to add after
we have an install base and no telemetry.

### I. Reconnect / roaming hardening
Sessions die on WiFi roams, AP handoffs, brief radio drops. A receiver that
silently re-establishes the USB/IP session (with port survival) is the
difference between "novelty" and "I leave this connected all day."

---

## 2. Recommendation

**Pick A — Hardware validation hardening.**

Reasoning:

- v0.2/v0.3/v0.4 already encode the product. We have a sender, a receiver, a
  protocol, a GUI, pairing. The blocker on shipping is not features; the
  blocker is that **nothing on real hardware has been demonstrated green
  twice in a row** and nothing in CI catches a regression. We are one
  refactor away from silently breaking the whole stack and not noticing.
- The smallest scope that maximally moves us toward "people install it and it
  just works" is the scope that converts our existing claims into testable,
  CI-enforced truth. Everything downstream (Windows port, isoc transfers,
  multi-device) is built on top of an assumption that the Linux+Android path
  works. If that assumption is wrong, every later theme inherits the bug.
- It is also the theme with the lowest research risk. We know exactly what
  needs to be built; the only unknowns are operational (where the runner
  lives, which devices to include).
- Bonus: it makes B (isoc transfers) cheap to evaluate later, because we will
  already have a UVC camera and a USB DAC physically wired into the runner.

Secondary recommendation: bundle **G (PSK rotation)** and **H (basic
structured logs + counters)** into v0.5 as small additions, because:

- G is a ~1-day change and v0.5 will be the first version we tell anyone to
  actually install, so "you cannot revoke a laptop" becomes embarrassing.
- H is also ~1-day and the E2E harness wants the counters anyway (it asserts
  on them).

We explicitly **defer** isoc transfers (B), Windows (C), macOS (D), reverse
direction (E), and multi-device (F) to v0.6+.

## 3. Deliverables — v0.5

### 3.1 Hardware E2E harness (core)

New top-level directory: `tests/hardware/`.

- `tests/hardware/README.md` — runner setup: which Pixel, which USB hub,
  which devices, how to flash, how to enroll the runner.
- `tests/hardware/runner/` — self-hosted GitHub Actions runner config.
  - `Dockerfile` for the runner image (Rust toolchain, `vhci-hcd` kernel
    module loaded on the host, `adb`, `gradle`).
  - `systemd/zerowire-runner.service` — runner lifecycle.
  - `udev/99-zerowire-test-devices.rules` — stable `/dev/zerowire-test-*`
    symlinks for the test USB devices, so test code does not rely on bus
    numbering.
- `tests/hardware/harness/` — Rust crate `zerowire-hwtest`.
  - `src/lib.rs` — `Harness` type: pair phone, start sender app via `adb
    shell am start`, start Linux receiver, attach, run scenarios, tear down.
  - `src/scenarios/hid_mouse.rs` — assert mouse moves register on receiver
    `evdev`.
  - `src/scenarios/hid_keyboard.rs` — assert keystrokes register.
  - `src/scenarios/mass_storage.rs` — write a 16 MiB file, read it back,
    verify checksum.
  - `src/scenarios/cdc_acm.rs` — open `/dev/ttyACM0`, loopback test against
    a known-good firmware on a Pi Pico.
  - `src/scenarios/reconnect.rs` — kill the TCP connection mid-transfer,
    assert session re-establishes and the next transfer succeeds.
- `tests/hardware/bin/zerowire-hwtest` — CLI wrapper so a human can run
  scenarios locally with the same code CI runs.

### 3.2 CI wiring

- New GitHub Actions workflow: `.github/workflows/hardware-e2e.yml`.
  - Triggers: `pull_request` (label `hw-e2e`) and nightly `schedule`.
  - Runs on the self-hosted runner with label `zerowire-hw`.
  - Steps: build sender APK, install on phone, build Linux receiver, run
    `zerowire-hwtest --all`, upload artifacts (logs, pcaps if `tcpdump`
    capture is on).
- Existing `ci.yml` (from PR #6) stays the gating check on regular PRs;
  `hardware-e2e.yml` is gating only on PRs touching `android-sender/`,
  `desktop-linux/`, or `protocol/`.

### 3.3 PSK rotation (small add)

- `protocol/src/auth.rs` — `Identity` becomes `{ psk: Psk, created_at:
  SystemTime, expires_at: Option<SystemTime>, label: String }`. PSK store
  becomes a list, not a single value.
- `protocol/src/auth.rs` — new `revoke(label: &str)` and `rotate() -> NewPsk`
  on the store.
- `desktop-linux-gui/src/pairing.rs` — paired-devices list shows label +
  created date + a `Revoke` button.
- `android-sender/.../PairingStore.kt` — same model on the Android side, with
  Compose UI list of paired receivers.
- Tests: rotate, revoke, expired PSK is rejected at handshake.

### 3.4 Observability (small add)

- `protocol/src/metrics.rs` — single `Counters` struct: `bytes_tx`,
  `bytes_rx`, `urbs`, `reconnects`, `auth_failures`. Atomic, lock-free.
- Wire `tracing` through `protocol/`, `desktop-linux/`,
  `desktop-linux-gui/`. Replace ad-hoc `println!` with `tracing::info!` /
  `debug!` / `warn!`.
- `desktop-linux/src/bin/zerowire-stats` — tiny CLI that dumps current
  counters from the running daemon over a Unix socket. Useful for the E2E
  harness assertions.
- Android: route Kotlin `Log` through Timber, add a "copy diagnostics" button
  in the Compose UI that dumps the last 5 minutes of logs to share.
- **No** Sentry / external crash reporting in v0.5. Defer; it has a privacy
  and infra story we are not ready to write.

### 3.5 Docs

- `docs/v0.5-hardware-harness.md` — how the runner is provisioned, how to
  reproduce locally, how to add a new scenario.
- `docs/v0.5-pairing-rotation.md` — operator guide to rotating and revoking
  PSKs.
- Update `README.md`: "Supported platforms" table now shows tested-in-CI
  checkmarks vs. "claimed."

## 4. Risks

### Hardware-gated

- The self-hosted runner needs an actual Pixel physically wired to a machine
  that lives somewhere with network and power. Until that exists, none of
  3.1 / 3.2 can be merged green. Mitigation: prototype against a phone on
  Nilesh's desk before we worry about the permanent host.
- ADB authorization is a real headache on long-lived runners (phone forgets
  the host after reboot). Mitigation: enroll the runner's public key in
  `/data/misc/adb/adb_keys` once, document it, and check it in the harness.
- Phones drop off USB after thermal events, OTA updates, and locked-screen
  USB policy changes. The harness must treat "phone not visible" as
  retryable, not as a hard test failure, or every Tuesday will be red.

### Research-gated (not in v0.5, but blocks v0.6 planning)

- We are deferring isoc-transfers until after the harness exists, but the
  feasibility audit (theme B) needs to happen during v0.5 in parallel so we
  know what v0.6 is. Spike, not implementation.

### Scope creep

- "While we are in `protocol/src/auth.rs` anyway" is how PSK rotation grows
  into a full identity rework. Hold the line: list-of-PSKs, rotate, revoke,
  expiry. No certificates, no PAKE upgrade, no key escrow.
- "While we are adding tracing anyway" is how observability grows into a
  metrics pipeline. Hold the line: in-process counters + structured logs +
  a Unix socket dump. No Prometheus exporter in v0.5.

### Schedule

- 3.1 + 3.2 is the bulk of the work and the part with the most operational
  unknowns. 3.3 and 3.4 are bounded. If 3.1/3.2 slip, cut 3.4 first (logs
  are nice; the harness is the product); keep 3.3 because it ships with the
  first real install.

---

## 5. Out of scope for v0.5 (explicit)

- Isochronous transfers (theme B) — feasibility spike only.
- Windows receiver (C).
- macOS receiver (D).
- Reverse direction (E).
- Multi-device per session (F).
- External crash reporting (part of H).
- Roaming / connection-survival hardening (I) — partly tested by the
  reconnect scenario in 3.1, but not productized.

These are not rejected; they are sequenced. v0.6 candidate is **C (Windows
receiver)** if the isoc spike comes back negative, or **B (isoc transfers)**
if it comes back positive.
