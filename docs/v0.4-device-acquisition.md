# zerowire v0.4 — device acquisition + UI

PR #4 landed the URB pump, but the pump consumes a `UsbDeviceConnection`
that nothing in the APK was acquiring yet. v0.4 fills that gap and
puts a real UI on both ends.

## Android sender

```
+---------------+  USB attach  +---------------+
|  MainActivity |<-------------|  Android OS   |
|  (Compose)    |   broadcast  +---------------+
+-------+-------+
        | bind+set state
        v
+---------------+   start sharing   +-------------------+
|  ViewModel    |------------------>|  UsbAcquisition   |
|               |    permission     |    .requestPerm  ()
|               |<------------------|    .open ()       |
+-------+-------+                   +---------+---------+
        |                                     |
        | binder API                          | UsbDeviceConnection
        v                                     v
+-------+-----------------+        +----------+----------+
|  SenderService          |        |  UsbIpHost (pump)   |
|   - foreground notif    |<-------|   - control/bulk    |
|   - mDNS advertise      |   bytes|   - interrupt       |
|   - accept loop         |        |   - bytes counter   |
+-------------------------+        +---------------------+
```

### What's new vs v0.3

* `UsbAcquisition` (new) — single source of truth for enumeration,
  permission requests (with the correct `PendingIntent.FLAG_MUTABLE`
  on API 31+), `openDevice()`, and bulk `claimInterface()`.
* `SenderViewModel` + `MainScreen` — Compose UI driven by a `StateFlow`
  off the service binder. No more XML.
* `SenderService` notification — `connectedDevice` foreground type
  with device name, receiver endpoint, live bytes/sec, and a Stop
  action.
* `PairingPayload` — `zerowire://pair?host=…&port=…&code=…` URI shared
  with the desktop QR generator.
* `SettingsStore` — DataStore-backed receiver-address memory.

### Why a fresh permission request per-share

v0.3 asked permission for every plugged-in device on `MainActivity.onCreate`.
That was fine for the walking-skeleton workflow but produced a "permission
fatigue" UX where the user got prompted before they'd decided what to
share. v0.4 only asks for the device the user explicitly taps **Share**
on, which matches Android's own "use this app with this device?" mental
model.

### Notification updates

A single dedicated thread inside the service samples the URB pump's
`bytesTransferred` counter once per second and re-renders the
notification. Sampling here (not in the pump) keeps the hot path free
of clock calls and rate-limits the notifications regardless of how fast
bytes flow.

## Desktop Linux receiver

The existing `zerowire-cli` keeps working unchanged — it's still the
headless / CI path. The new `zerowire-gui` (in `desktop-linux-gui/`)
is a thin egui window wrapping the same CLI as a subprocess:

* Generates a 12-char pairing code, renders it into a QR code with
  the `qrcode` crate, and displays it next to a `zerowire://pair?…`
  URI for QR-scanner apps.
* Tails the CLI's stdout/stderr; greps for `HELLO_ACK`, `session
  ended`, `ATTACH_DENIED` to drive the UI state machine.
* Stop button kills the subprocess (and the SIGTERM handler in the
  CLI tears the receive loop down cleanly).

The tray-icon path is gated behind `--features tray`; default builds
just have the window so a clean cargo build works on minimal Linuxes
(no `libayatana-appindicator3-dev` headers required).

## What's deliberately deferred to v0.5

* Multi-device-at-once UI on the phone. The acquisition layer can
  handle it (each `AcquiredDevice` is independent), the service just
  doesn't expose the binder hook yet.
* In-GUI device hotplug. Devices currently only show up when the
  CLI logs them; richer IPC will come with a JSON daemon protocol.
* Auto-mount of mass-storage on the desktop side. The kernel sees
  the device via `vhci-hcd`; the user runs `udisksctl mount` for now.
